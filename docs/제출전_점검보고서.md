## 1. 프로젝트 목적

이 프로젝트는 AMR 관제 서버와 현장 설비 사이의 상태 전달 및 출력 제어를 구현한다. 설비는 적색·황색·녹색 경광등, 부저, 푸시 버튼으로 구성된다. 라즈베리파이에서는 GPIO로 장치를 다루고, Windows·macOS에서는 동일한 인터페이스의 가상 GPIO로 동작한다.

수업 시연에서는 하드웨어 없이 버튼 입력과 출력 상태가 관제 화면에 전달되는 과정을 확인할 수 있다. 로봇 이동까지 시연하려면 별도의 MQTT 브로커와 호환 AMR 클라이언트를 준비해야 한다.

## 2. 시스템 구성과 통신 흐름

| 구성 요소 | 주요 파일 | 역할 |
|---|---|---|
| FMS 서버 | `fms_server/main.py` | FastAPI 기반 REST·WebSocket, 사이트·지도·로봇·작업 관리 |
| 작업 처리 | `fms_server/task.py` | Move·Wait·Signal·Output 단계 처리와 대기열 관리 |
| 로봇 통신 | `fms_server/mqtt_client.py` | MQTT 로봇 상태 수신과 명령 발행 |
| 설비 서버 | `server/io_server.py` | GPIO 제어, Socket.IO 상태 전달, 출력 HTTP 요청 수신 |
| 가상 GPIO | `server/mockgpio.py` | PC에서 핀 상태와 입력 엣지 콜백 재현 |
| 신호 업로드 | `server/fms_uplink.py` | 설비 원시 상태를 FMS 플래그 API로 전달 |
| 관제 웹 | `web/fms.html` | 지도, 로봇, 작업 단계, 현장 신호 표시 |
| 설비 웹 | `web/pi.html` | 버튼 입력·출력 수동 시험 및 핀 상태 확인 |
| 공용 모델 | `common/` | 메시지 스키마, 지도 좌표·주석 모델 |

통신 흐름은 다음과 같다.

```text
AMR 클라이언트 ← MQTT 브로커 → FMS 서버 ← REST / WebSocket → 관제 웹
                                   ↑              
                          HTTP 신호 업로드
                                   │
라즈베리파이 / 가상 GPIO ← 설비 서버 ← HTTP 출력 명령 ← FMS 작업 처리
                              ↕ Socket.IO
                            설비 웹
```

푸시 버튼 입력은 GPIO 상태 변화 → 설비 서버 → FMS 플래그 순서로 전달된다. 출력은 반대로 FMS의 `set_output` 단계가 설비 서버의 `POST /api/output`을 호출하여 변경한다. 설비 서버는 상태 변경 시 즉시, 이후 약 2초 주기로 신호를 다시 전송한다.

관제 웹은 로봇 MQTT 메시지를 직접 구독하지 않는다. 로봇 상태는 FMS의 WebSocket으로, 지도는 FMS의 REST API로 받는다.

## 3. 구현 범위와 한계

### 확인한 구현

- 사이트·지도 업로드 및 활성 버전 관리, 로봇 등록과 지도 배정
- 이름 있는 목적지 저장과 지도 표시
- 이동, 시간 대기, 신호 조건 대기, 설비 출력 단계를 포함하는 작업 구성
- 작업 대기열, 실행·취소 및 로봇 보고에 따른 상태 갱신
- 신호 조건 유지 시간, 제한 시간과 제한 시간 초과 처리
- 신호 갱신이 6초를 넘으면 조건 만족으로 간주하지 않는 처리
- 경광등 한 색 점등 규칙, 부저 출력, 버튼 입력
- 실제 GPIO를 사용할 수 없는 PC에서 가상 GPIO 자동 사용

### 별도 준비 또는 미구현 항목

| 항목 | 현재 상태 |
|---|---|
| MQTT 브로커·AMR 클라이언트 | 별도 구성 요소이며 이 프로젝트에 포함되지 않음 |
| 로봇 없이 작업 실행 | 현재 작업 처리의 로봇 가용 조건을 충족할 수 없음. 수동 I/O 시험은 가능 |
| 다중 로봇 트래픽 제어·교착 해소 | `traffic.py`는 구현 예고 수준 |
| 비용 기반 작업 할당·경로 계획·충전 스케줄링 | 관련 파일은 골격 수준 |
| 사용자 인증·권한·HTTPS | 구현 범위 밖 |
| 실물 라즈베리파이·배선 | 이번 점검에서 검증하지 않음 |
| 완전 오프라인 실행 | Socket.IO 클라이언트를 CDN에서 읽으므로 현재 구성에서는 불가 |

기반 FMS는 별도 프로젝트에서 가져온 사본이다. 출처는 [FMS_SOURCE.md](../FMS_SOURCE.md)에 기록되어 있다. 과제의 추가 구현과 기반 코드를 구분해 설명해야 한다.

## 4. UI 점검 및 개선

기존 지도 중심 구조와 Monitor / Jobs / Signals 탭을 유지했다. 새로운 디자인 체계를 덧붙이기보다 관제에 필요한 정보의 위계와 용어를 조정했다.

| 변경 | 목적 |
|---|---|
| 화면 제목을 FMS / Fleet control로 정리 | 화면 역할을 짧게 표시 |
| 헤더에 Site setup 링크 추가 | 최초 사이트·지도·로봇 설정으로 바로 이동 |
| 단계 버튼의 장식용 기호 제거 | 운영 기능의 이름을 중심으로 표시 |
| Flag·Pin 버튼을 Signal·Output으로 변경 | 입력 조건과 출력 제어의 의미를 명확히 전달 |
| 패널·탭·상태 배지의 둥근 모서리 축소 | 지도와 조작 패널의 구분 정돈 |
| 로봇이 없는 경우 연결 필요 안내 | 빈 화면의 이유와 다음 행동 제시 |
| I/O 서버 연결 실패와 클라이언트 로딩 실패 문구 구분 | 서버 미실행과 인터넷/CDN 문제를 구분 |
| 키보드 포커스 표시와 선택 상자 접근성 이름 추가 | 키보드 이동 및 요소 식별 개선 |

관제에 필요한 지도와 상태 정보를 중심으로 화면 표현을 정돈했다. 로봇 표시값과 연결 상태는 실제 수신 데이터에 기반한다.

브라우저 자동 제어 호스트에 연결할 수 없어 실제 화면 배치·작은 화면·키보드 조작의 시각 검수는 완료하지 못했다. JavaScript 구문과 웹 자원 응답은 별도로 확인했다.

## 5. 실행과 배포 준비

### 추가한 실행 파일

| 파일 | 동작 |
|---|---|
| `run.py` | Python 버전·포트 확인, 가상환경·패키지 준비, 두 서버 실행, 접속 대기, 브라우저 열기, 종료 정리 |
| `start.bat` | Windows에서 공통 실행기 호출 |
| `start.command` | macOS에서 공통 실행기 호출 |
| `.gitignore` | 가상환경·캐시·OS 임시 파일 제외, 예제 맵 포함 유지 |
| `.github/workflows/test.yml` | GitHub의 macOS·Windows / Python 3.12 테스트 구성 |

실행기는 기존 프로세스를 종료하지 않는다. 8000 또는 5001 포트가 사용 중이면 오류를 안내한다. 시작한 서버는 같은 터미널에 로그를 표시하고 Ctrl+C 시 정리한다. 첫 실행은 패키지 다운로드 시간이 필요하며 Python 자체 설치는 사용자가 해야 한다.

README에는 Python 설치, GitHub ZIP·clone 다운로드, 운영체제별 실행, 접속 주소, 하드웨어 없는 첫 시연, 로봇 연결 조건, 설정, 수동 실행, 테스트와 오류 해결을 작성했다.

### GitHub 제출 상태

제출 저장소는 [DaeHwanZZang/fms-io](https://github.com/DaeHwanZZang/fms-io)이다. 기존 `main` 이력을 기반으로 현재 프로젝트를 반영하며 README에 실제 clone 주소와 ZIP 다운로드 링크를 기재했다. 코드 커밋 `8f3d186`을 `main`에 업로드하고 GitHub에서 새 폴더로 clone했다. 내려받은 사본도 기존 macOS 가상환경에서 전체 테스트 125개를 통과했다(36.71초).

[GitHub Actions 실행 결과](https://github.com/DaeHwanZZang/fms-io/actions/runs/43179061802)에서 macOS·Windows / Python 3.12의 새 의존성 설치, 실행기 구문 검사와 전체 테스트가 모두 통과했다. macOS는 125 passed / 46.68초, Windows는 125 passed / 143.31초였다. 각 환경에서 경고 1건이 있었다. 배치 파일 더블클릭과 실제 브라우저 조작은 CI의 검증 범위에 포함되지 않는다.

## 6. 검증 결과

### 자동 테스트

프로젝트 루트에서 다음 명령으로 실행했다.

```sh
.venv/bin/python -m pytest fms_server/tests server -q
```

| 항목 | 결과 |
|---|---|
| 수정 전 기준 실행 | 40 passed / 27 failed / 58 errors |
| 주요 실패 원인 | 포함되지 않은 `AMR_client/maps/...` 참조 |
| 수정 | 테스트 공용 경로를 동봉된 벤더 원본 맵으로 변경 |
| 수정 후 전체 실행 | **125 passed / 1 warning / 38.86초** |
| 경고 | Starlette TestClient의 httpx 사용 중단 예고. 현재 실행 실패는 아님 |

외부 저장소를 심볼릭 링크로 연결하지 않고 전체 테스트가 통과했다. 애플리케이션의 로봇·작업 처리 동작은 이번 작업에서 수정하지 않았다.

로그: [pytest-macos.txt](verification/pytest-macos.txt)

### 실제 서버 연동 확인

공통 실행기로 두 서버를 포그라운드 실행하고 다음을 확인했다.

| 확인 항목 | 결과 |
|---|---|
| FMS `/health` | HTTP 200, `status=ok` |
| 관제 페이지 `/ui/fms.html` | HTTP 200 |
| 설비 페이지 `:5001/` | HTTP 200 |
| 활성 지도 메타데이터·이미지·주석 | REST 경로에서 모두 응답 확인 |
| 부저 HTTP 출력 요청 → 가상 GPIO → FMS 플래그 | 상태 변경 확인 |
| 시험 종료 후 부저 | 원래 상태로 복구 확인 |
| FMS 웹 JavaScript 구문 | Node 구문 검사 통과 |
| `run.py` 및 macOS 셸 진입점 | Python 컴파일·zsh 구문 검사 통과 |
| 중복 실행·종료 | 사용 중인 포트 감지 후 시작 거부, Ctrl+C 후 두 포트 해제 확인 |

MQTT는 미연결이고 실제 로봇 수신 수는 0이었다. 사이트 1개와 과거 작업 31개는 기존 예제 데이터로 로드되었다. 이 기록은 이번 시험에서 실행한 작업의 성과가 아니다.

로그: [smoke-macos.txt](verification/smoke-macos.txt)

### 검증의 한계

- Windows CI에서 패키지 설치와 테스트는 통과했다. Windows 데스크톱에서 배치 파일 더블클릭·브라우저 실행은 직접 검증하지 않았다.
- 로컬 실행과 새 clone 테스트는 기존 macOS 가상환경을 사용했다. CI에서는 새 환경에 패키지를 설치했다. 공통 실행기의 첫 가상환경 생성부터 브라우저 열기까지 이어지는 빈 PC 전체 경로는 별도 확인이 필요하다.
- 실제 브라우저의 지도 렌더링과 반응형 배치는 시각 검수하지 못했다.
- 실제 AMR 주행, MQTT 연결 및 GPIO 실배선 시험은 수행하지 않았다.
- 의존성은 최소 버전 조건이며 완전 고정된 잠금 파일이 없다. 향후 설치 시 패키지 조합이 달라질 수 있다.
